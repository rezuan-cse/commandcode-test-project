# Taste
- Wants a plan shared before any code is written. Asks explicitly: "share me your plan before start coding" and again "Share your plan first on it before going further." Confidence: 0.9
- When exploring a product/scope decision, sometimes asks for analysis only ("no code, just share your thoughts") and expects the tradeoffs, a clear recommendation, and honest caveats before any implementation. Confidence: 0.55
- Expects the assistant to start by reading project/folder instructions (e.g., README, INSTRUCTIONS files, .commandcode config) before planning. Confidence: 0.7
- Prefers multi-phase plans delivered one phase at a time: detailed first phase + summarized later phases, with a pause/re-plan between phases after each acceptance gate. Confidence: 0.65
- Prefers concrete, verifiable acceptance criteria in plans — specific numbers, named outputs, and "this must equal that" checks over vague goals. Confidence: 0.7
- When real data is on hand (e.g., client workbook), prefers a working demo that runs the real data through real logic over a clickable mock with fake numbers. Confidence: 0.6
- Prefers the demo/prototype codebase to carry forward into the production build (one codebase, growing in scope) rather than being thrown away and rebuilt. Confidence: 0.6
- Prefers deploying demos on free-tier / no-cost hosting ("on free tier") rather than paid plans — when offered "keep the free instance awake" vs "pay $7/month for a non-sleeping instance", picks the free workaround. Confidence: 0.75
- Prefers fixing hosting/ops annoyances with the lowest-friction option that needs no new third-party account or re-platforming (chose a scheduled keep-alive workflow over migrating to Vercel/Netlify or signing up for an uptime service). Confidence: 0.5
- Wants demos deployed to a shareable public URL so the client can click through it themselves and send back observations/new requirements. Confidence: 0.55
- When reporting a bug, expects the fix to be completed and then committed and pushed to git ("recheck fix and push the git") — the app is deployed and used publicly, so changes must land on the remote/live deployment, not just locally. Confidence: 0.7
- Wants visible live progress in the CLI while multi-step work runs — checks repeatedly ("can't I see the progress in CLI?", "What is the update? Is it done?") and loses patience if turns pass without tool calls/output. Expects a plain done/not-done status with what is verified working versus still outstanding. Confidence: 0.7
- Delegates outcome-level goals with terse, open-ended instructions ("do whatever you need to do and make it live") and expects the agent to work out the necessary steps and carry them through autonomously rather than asking for direction. Confidence: 0.5
- Prefers to communicate requirements and problems with visual evidence — pastes browser screenshots of bugs/mismatches and images of handwritten diagrams or sketches of client expectations directly into the chat rather than only describing them in text. Confidence: 0.7
- After making a change that fixes a previously-failing check, expects the same empirical test to be re-run against the live system to prove it ("repeat the marker test again and let me know the update") and wants a before/after result — verification by re-testing, not assumption. Confidence: 0.55
- Wants business/statutory rules (VAT, TAX, AIT rates and similar) to be configuration data an admin can edit at runtime rather than hardcoded, with a free-form metadata field so admins can attach extra fields without a schema change. Accepts clearly-flagged placeholder values ("standard Bangladeshi VAT/TAX/AIT rule as a placeholder") until the client/Tax adviser confirms the real ones. Confidence: 0.65
- When new client requirements arrive, expects them first reconciled against the existing spec, the real data (workbook), and what is already built — an "is this aligned with client expectations / what is missing" gap analysis with an aligned-vs-missing verdict — before any implementation. Confidence: 0.55
- Expects the demo to behave like the eventual production product rather than take shortcuts: features/menus a role cannot use should be hidden or restricted rather than shown and then refused. Explicitly checks that "in the final production version those options will be invisible which are not permitted to show the respective users" and wants the demo brought in line. Confidence: 0.65
- Wants user-facing restriction/error messages written for non-technical end users — a friendly, plainly-worded notice explaining the rule — not raw technical messages that expose internal identifiers (e.g., resource keys) or read like a fault. Confidence: 0.6
- When flagging a problem in one place, expects the fix applied consistently across every section where it applies ("apply it for every section where required"), not only at the reported spot. Confidence: 0.55
- Expects claims about how a screen/feature actually behaves (e.g., "you should see X") to be grounded in observing the rendered running result, not inferred from the code — repeatedly catches the assistant describing UI behaviour from reasoning and quotes the earlier claim to point out the mismatch. Confidence: 0.6
